# Электронные счета (XRechnung / ZUGFeRD)

Состояние: 2026-10-11, не закоммичено.

## Правила (проверены по письму BMF от 15.10.2025, текст в `einvoice-2026-10-11/`)

- **Приём:** с 01.01.2025 каждый предприниматель должен уметь принимать e-Rechnung, и Kleinunternehmer тоже. Для приёма по e-mail отдельный ящик не нужен.
- **Выставление:** с 01.01.2027 обязательно при обороте больше 800 000 € за прошлый год, с 01.01.2028 — для всех в B2B. Освобождены: счета до 250 €, счета Kleinunternehmer, проездные билеты.
- **Допустимые форматы:**
  - всё, что соответствует EN 16931, в том числе XRechnung (UBL или CII);
  - ZUGFeRD начиная с 2.0.1, кроме профилей MINIMUM и BASIC-WL.
- **Хранение и вычет:**
  - структурированную часть хранить в исходном виде без изменений;
  - вычет входного НДС — только по XML. Картинка гибридного PDF — лишь копия.

## Аудит модуля счетов (2026-10-11)

- Ошибки из аудита 2026-10-02 исправлены:
  - налог считается через `computeTax`;
  - повтор счёта в конце месяца исправлен;
  - есть отправка счетов и напоминания.
- Электронных счетов не было совсем — ни приёма, ни выставления.
- **Чего не хватает для выставления по EN 16931:**
  - адрес продавца разбит на поля (сейчас только `addressLines`);
  - то же для адреса покупателя (сейчас только `billingAddress`);
  - BT-10 Buyer reference (в XRechnung обязателен);
  - электронный адрес покупателя;
  - единицы измерения строк (UN/ECE Rec 20);
  - дата или период поставки;
  - раздельные VAT ID и Steuernummer у продавца (сейчас одно поле `taxId`).

## X1 — приём (сделано)

- **`modules/e-invoices/einvoice-reader.ts`** читает:
  - UBL Invoice и CreditNote;
  - CII CrossIndustryInvoice;
  - XML отдельным файлом или вложенный в PDF (factur-x.xml, zugferd-invoice.xml, xrechnung.xml) через pdf-lib.

  Парсер `fast-xml-parser` (сущности не раскрываются). `fast-xml-parser` и `pdf-lib` теперь объявлены как продовые зависимости, версии те же, что уже были установлены.
- **Подключение:** в `ReceiptProcessorService.processReceipt` до OCR. Через него проходят все пути загрузки: скан, загрузка чеков, Telegram, webhooks.
  - Цифры берутся из XML, confidence = 1, `extractionMethod = einvoice_xml`.
  - В `parsedData.einvoice` сохраняются: профиль, номер, сроки, IBAN, продавец, разбивка НДС, признак reverse charge.
- **Загрузка XML:**
  - XML разрешён как чек, только если внутри счёт (`isEInvoiceXml`);
  - выписка camt как чек отклоняется;
  - `FileType.XML` — миграция `1787160000000`, только добавляет значение enum.
- **Контрагент:**
  - если у контрагента ещё нет страны и VAT ID, они берутся у продавца из счёта, и строка пересчитывается — reverse charge по поставщику из ЕС включается сам после выбора категории;
  - заполненного контрагента не трогаем;
  - номер проверяется в VIES ежедневной задачей, которая перепроверяет непроверенные номера.
- **Предупреждения:**
  - ZUGFeRD MINIMUM и BASIC-WL — `einvoice_not_en16931`;
  - сумма НДС по строкам не сходится с итогом — `einvoice_totals_disagree`.
- **UI:** `EInvoicePanel` на странице документа `/storage/receipts/[id]`. Тексты на 35 языках. В выборе файлов разрешён `.xml`.
- **Тесты:**
  - фикстуры — официальные образцы (Apache-2.0): 20 пар KoSIT XRechnung 3.0.2 в UBL и CII, 5 PDF из корпуса ZUGFeRD;
  - юнит: 30;
  - e2e: 7;
  - ранее существовавшие e2e загрузки: 37 зелёных.
- **Находки:**
  - в официальном кейсе 01.21a у UBL и CII разные VAT ID продавца; это отмечено в тесте;
  - немецкое «Gutschrift» — самовыставленный счёт (код 389), а не кредит-нота.
- **Проверено вживую** на dev: ZUGFeRD PDF → сумма 2000, номер 47110818, панель на странице.
- **Не сделано:**
  - тот же хук для Gmail-парсера (у него свой путь для PDF);
  - строки НДС из счёта не переносятся в транзакцию — НДС считается нашим движком по категории;
  - мы не определяем, наш ли это исходящий счёт (сейчас любой счёт считается входящим).

## X2 — выставление (сделано, не закоммичено)

- **Данные** — миграция `1787170000000-AddEInvoiceIssueFields` (только nullable/default колонки, восьмая для db-approved):
  - реквизиты: `street`, `postal_code`, `city`, `tax_number` (Steuernummer отдельно от VAT ID в `tax_id`), `contact_name`;
  - клиенты: адрес по полям, `country_code`, `buyer_reference`, `supply_type`;
  - счета: `buyer_reference`, `delivery_date`;
  - строки: `unit_code` (по умолчанию C62).
  - Свободный адрес оставлен для печати; данные не переносятся — угадывать улицу и индекс из текста ненадёжно.
- **`modules/e-invoices/xrechnung-writer.ts`** — чистая функция, XRechnung 3.0 в CII.
  - Разбивка НДС по EN 16931 (BR-CO-17): налог считается один раз на сумму по категории и ставке. Поэтому он может на цент отличаться от построчного округления в PDF; юридически значим XML.
  - `missingForXRechnung` проверяет правила BR-DE-2/5/6/7/15/19, BR-S/E-02, BR-AE/K-02, BR-IC-11 и возвращает список вместо битого файла.
  - Поставка в ЕС получает адрес доставки (BR-IC-12, BR-DE-10/11).
- **Категории:**
  - ставка RC → AE (услуги) или K (если у клиента указано «товары»);
  - EXEMPT → E с названием ставки как причиной;
  - 0 % → Z;
  - строка без ставки: у Kleinunternehmer — E с текстом про § 19, у плательщика НДС — ошибка `line_tax_rate`.
- **`InvoiceXRechnungService`** и эндпоинты `GET /invoices/:id/xrechnung` (файл или 400 `XRECHNUNG_INCOMPLETE` со списком) и `GET /invoices/:id/xrechnung/check`. В письмо со счётом немецкой компании XML прикладывается к PDF, если его можно собрать.
- **Проверка официальным валидатором:** `backend/scripts/validate-xrechnung.sh` (KoSIT validator 1.6.3 + XRechnung 3.0.2 config, eclipse-temurin:21-jre в docker).
  - 5 сценариев генератора приняты без ошибок и предупреждений: обычный, две ставки, reverse charge, Kleinunternehmer, поставка товаров в ЕС;
  - 2 счёта, выданные через API в e2e, тоже приняты.
  - Первый прогон поймал BR-IC-12 и BR-DE-10/11 — исправлено.
- **Тесты:** writer unit 10 (включая обратное чтение своим парсером), e2e 3; прежние e2e smb и einvoice-receive зелёные.
- **UI:**
  - реквизиты: новые поля и подсказка;
  - клиент: блок «Для электронных счетов»;
  - счёт: дата поставки, ссылка покупателя, единица в строке, кнопка «XRechnung (XML)» со списком недостающего;
  - словарь `einvoiceFields`, тексты на 35 языках.
- **Не сделано в X2** (закрыто в X3, кроме Peppol): ZUGFeRD, кредит-ноты, скидки и надбавки, Peppol.

## X3 — доделки (сделано, не закоммичено)

- **PDF:** печатает дату поставки (Leistungsdatum) и ссылку покупателя. Адрес клиента берётся из полей street/postal/city/country, если свободный адрес пуст (§ 14 UStG требует адрес получателя; раньше клиент, заполненный только для XRechnung, печатался без адреса).
- **Кредит-ноты как XRechnung:** тип 381, ссылка на исправляемый счёт (InvoiceReferencedDocument).
  - Эндпоинты `GET /credit-notes/:id/xrechnung(/check)`; кнопка «XRechnung (XML)» у каждой кредит-ноты в карточке счёта.
  - Строки кредит-ноты копируют единицу и скидку исходного счёта.
- **Скидки и надбавки в строке** — миграция `1787180000000-AddLineAdjustments`: `adjustment_percent` у строк счёта и кредит-ноты, плюс `unit_code` у строк кредит-ноты. Это девятая миграция для db-approved.
  - Знак задаёт вид: минус — скидка, плюс — надбавка; допустимо от −100 до 1000.
  - Сумма строки = qty × price ± округлённая поправка (BR-LIN-04). Один расчёт `lineAmount` на всё: итоги, проводки, PDF, XML; во фронте его копия.
  - XML: строковая AllowanceCharge (BG-27/28): процент, база, сумма; у скидки код 95. Цена нетто — до поправки. При ценах с НДС поправка в нетто считается как разница двух расчётов строки.
  - PDF: «Discount 10%» / «Surcharge 15%» под описанием, на 20 языках документов.
  - UI: поле «± %» под ценой.
  - Скидки на весь документ (BG-20/21) не делались: в счёте нет такого поля.
- **ZUGFeRD:** `modules/e-invoices/zugferd.ts`. PDF/A-3b, XRechnung вложен как `xrechnung.xml` (AFRelationship Alternative, /AF), XMP с pdfaid и схемой fx (ConformanceLevel XRECHNUNG), OutputIntent sRGB. Профиль sRGB — компактный, CC0, вшит в код.
  - Когда собирается: при отправке счёта и выпуске кредит-ноты, внутри той же транзакции, если продавец из DE и XRechnung собирается без пропусков. Иначе PDF остаётся обычным.
  - `GET /invoices/:id/xrechnung` у отправленного счёта отдаёт XML, вшитый в PDF, без изменений, даже если клиента потом поправили (BMF: обязателен XML, его надо хранить неизменным).
  - В письме: если PDF уже гибридный, отдельный XML не прикладывается — один электронный счёт на письмо.
  - Проверка: `backend/scripts/validate-zugferd.sh` (Mustang CLI 2.26.0: veraPDF для PDF/A-3 и схематрон EN 16931 + XRechnung). Валидны:
    - юнит-гибрид, в том числе с PNG-логотипом с прозрачностью;
    - счёт и кредит-нота из e2e;
    - живой счёт на dev.
- **Тесты:**
  - unit: pricing 3, writer + сценарий `line-adjustments`, zugferd 1, document +2;
  - e2e `xrechnung-issue`: скидка, гибрид, неизменность XML, PDF кредит-ноты;
  - integration: credit-notes и invoices-lifecycle.
  - KoSIT принимает все сценарии, e2e-файлы и живую кредит-ноту.
- **Peppol:** не код, а выбор провайдера Access Point — см. отдельный раздел.

## Peppol — варианты (разбор 2026-10-11, ничего не сделано)

- **Свой Access Point** не подходит self-hoster'у. Членство OpenPeppol для AP+SMP стоит от €2 750 в год плюс €2 500 за сертификацию (https://peppol.org/join/fees/). Ещё нужны соглашение с KoSIT как Peppol Authority, тесты в Testbed, PKI-сертификат, SLA. Это имеет смысл только для одного хостингового оператора, на phase4 (Apache-2.0).
- **Модель «свой ключ»: пользователь заводит аккаунт у провайдера AP, Lumio отправляет через его API.**
  - **Recommand** (BE, исходники AGPL-3.0). Принимает готовый UBL **или CII**: наш XRechnung уходит как есть. Знает Leitweg-ID, входящие приходят через вебхуки с HMAC. 25 документов в месяц бесплатно, дальше €0,30 за документ. https://recommand.eu/en/pricing, https://docs.recommand.eu/
  - **Peppyrus** (BE). 100 исходящих в месяц бесплатно, входящие без лимита, XML передаётся в base64. Приём CII не проверен, вероятно нужен UBL. https://www.peppyrus.be/en
  - **Остальные:** e-invoice.be (только UBL, вход от €350), Storecove и ecosio (цены по запросу, для платформ), Qvalia, Billit, B2Brouter.
- **Формат.** Peppol BIS Billing 3.0 существует только в UBL. XRechnung 3.0 в CII — отдельный разрешённый тип документа, но получатель должен зарегистрировать его в своём SMP. Госорганы DE адресуются как `0204:<Leitweg-ID>`, Leitweg-ID указывается в BT-10. Получателям вне DE, прежде всего в Бельгии, где B2B через Peppol обязателен с 01.01.2026, нужен генератор UBL BIS 3.0.
- **Германия.** Для B2B канал свободный (e-mail допустим), обязателен только формат. Peppol нужен для B2G и для клиентов, которые сами его требуют.
- **Решение (2026-10-13):** делать оба пункта — сделано, см. ниже.

## P1 — Peppol через Recommand и UBL BIS 3.0 (сделано 2026-10-13, не закоммичено)

- **UBL BIS 3.0:** `modules/e-invoices/peppol-ubl-writer.ts` — счёт и кредит-нота (CreditNote, BillingReference) из того же `XRechnungInput`, что и XRechnung.
  - Стороны адресуются Peppol ID (EndpointID).
  - Строковые скидки и надбавки, без IBAN — без PaymentMeans.
  - `missingForPeppol`: без XRechnung-специфики, но с Peppol ID и buyer reference (R003).
  - `peppol-id.ts`: разбор `scheme:value`; подсказка по VAT ID — DE 9930, AT 9914, NL 9944, FR 9957, ES 9920, IT 0211, BE 0208 из номера VAT. Схемы сверены по коду Peppol v9.7; 9915 — не австрийский VAT.
  - XRechnung CII при наличии Peppol ID пишет его как BT-49/BT-34 вместо e-mail.
- **Проверка:** `backend/scripts/validate-peppol.sh` — правила CEN EN 16931 UBL 1.3.17 (готовый XSLT) и Peppol BIS v3.0.20 (схематрон, скомпилированный SchXslt), Saxon в Java-контейнере.
  - 6 сценариев генератора и UBL из e2e — без единого замечания.
  - Сломанный файл ловит BR-CO-15, PEPPOL-R003 и PEPPOL-R010, то есть валидатор не пустышка.
  - CII из e2e принят KoSIT.
- **Recommand по ключу пользователя:**
  - `modules/peppol/recommand.client.ts` — Effect, Basic auth, схемы ответов. Чтение повторяется при 429/5xx, отправка — никогда.
  - `peppol.service.ts`:
    - подключение: ключ проверяется, секрет шифруется, компания выбирается сама, если она одна;
    - lookup получателя;
    - выбор формата по тому, что получатель зарегистрировал в SMP: немецкому продавцу сначала XRechnung CII, иначе BIS;
    - Leitweg-ID (0204) должен совпадать с buyer reference;
    - запись о передаче создаётся до отправки; частичный уникальный индекс даёт 409 на повторную отправку, после failed — можно снова;
    - отправленный XML хранится (`document_xml`) и скачивается;
    - статус доставки опрашивается cron раз в 10 минут и при открытии журнала;
    - приём — опрос inbox раз в 10 минут или «Синхронизировать»: invoice/creditNote становятся чеками с source `peppol` через обычный e-invoice-ридер, остальное помечается прочитанным; `peppol_inbound_documents` не даёт дублей.
  - Эндпоинты: `integrations/peppol/{status,settings,sync}`, `DELETE integrations/peppol`, `POST peppol/lookup`, `POST|GET invoices/:id/peppol`, `POST|GET credit-notes/:id/peppol`, `GET peppol/transmissions/:id/document`.
- **Миграция `1787220000000-AddPeppol`:** `clients.peppol_id`, enum receipts `peppol`, таблицы `peppol_connections`, `peppol_transmissions`, `peppol_inbound_documents`. Нужен db-approved.
- **UI:**
  - карточка «Peppol (Recommand)» в интеграциях (общая форма; теперь она показывает причину ошибки бэкенда вместо общего «не удалось»);
  - поле Peppol ID в карточке клиента: подсказка по VAT и кнопка «Проверить»;
  - панель «Отправить по Peppol» с журналом на счёте и компактная кнопка у кредит-нот; видна только при подключённом Peppol;
  - тексты на 35 языках, коды ошибок в `apiErrors`.
- **Тесты:**
  - unit: writer 12, client 5;
  - e2e `peppol` 6 (fake Recommand через `global.fetch`; мутация выбора формата ловится);
  - contracts e2e (+Client.peppolId, PeppolTransmissionList, PeppolLookup);
  - vitest 5;
  - весь backend unit 4832 зелёный.
- **Не проверено:** настоящий Recommand. Нужен playground-ключ (app.recommand.eu → playground team → API key типа basic). Ответы API взяты из их OpenAPI и документации.
- **Не сделано:**
  - вебхуки (для self-hosted выбран опрос);
  - вложение PDF в UBL (BT-125);
  - UBL-вариант XRechnung;
