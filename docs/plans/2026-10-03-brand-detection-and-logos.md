# Распознавание бренда и иконка мерчанта: что есть в опенсорсе и что делать нам

Дата: 2026-10-03. Статус: исследование + план, ничего не реализовано.
Повод: в списке «Top spenders» видно `other`, `1 / 4`, `WeWork Kurfürstendamm`, `Nobelhart & Schmutzig` — названия как есть из чека/выписки, без канонического имени и без иконки.

## 1. Главный вывод

**Готового движка «строка из выписки → бренд + логотип», который можно поставить как зависимость, в опенсорсе нет.** Всё, что продаётся как «transaction enrichment» (logo.dev, Brandfetch, Context.dev, Ntropy), — закрытые API: мы бы отправляли им список мерчантов каждого self-hosted пользователя. Для Lumio это неприемлемо по умолчанию.

**Зато есть готовые данные промышленного качества, на которых такой движок собирается за несколько дней:**

| Источник | Что даёт | Объём | Лицензия |
|---|---|---|---|
| **name-suggestion-index** (osmlab/NSI) | канонические имена брендов и операторов, алиасы (`matchNames`), имена на разных языках, `brand:wikidata`, набор стран (`locationSet`), OSM-теги (= подсказка категории) | 19 119 брендов + 24 157 операторов, 80 364 варианта написания | BSD-3-Clause |
| **NSI `wikidata.json`** (в том же пакете) | официальный сайт бренда и URL логотипа с Wikimedia Commons | 23 677 сайтов, 19 838 логотипов на 27 582 QID | BSD-3-Clause (данные — из Wikidata, CC0) |
| **openenrichment** (steveharrison) | регулярки «текст транзакции → мерчант» + MCC + примеры реальных дескрипторов | ~550 мерчантов (AU-центричный) | данные CC0, код MIT |
| **simple-icons** | SVG-пути онлайн-брендов (Netflix, Spotify, PayPal…), которых нет в NSI | ~3 300 брендов | CC0-1.0 (сами логотипы — ТЗ владельцев) |
| **Nominatim** (у нас уже self-hosted) | POI по координатам чека → `brand`, `brand:wikidata`, `website` из OSM | вся OSM | ODbL (атрибуция) |

Наш резолвер = **очиститель дескриптора (свой) + индекс по NSI + уже существующий прокси иконок**. Ничего из этого не требует внешних платных API и не отправляет наружу ни одной строки транзакции (кроме домена при запросе фавикона — см. §7).

## 2. Что в Lumio уже есть (на этом строим)

- `backend/src/modules/vendor-icons/` — прокси иконок: домен → фавикон с DuckDuckGo, кеш в Redis (7 дней хит / 1 день мисс), валидация домена против SSRF, честный 404 → фронт падает на инициалы. **Домен → иконка уже решён, не хватает «мерчант → домен».**
- `frontend/app/vendor-icons/index.ts` — 36 вклеенных путей simple-icons (пакет целиком 16 МБ, его сознательно не ставили).
- `frontend/app/components/VendorIcon.tsx` — лесенка «вклеенная иконка → прокси по домену → инициалы». Готовый UI-контракт.
- `transactions.vendor_normalized` — **единственное, что сейчас похоже на распознавание бренда**: его заполняет LLM в `ai-category-classifier.helper.ts` (промпт «ТОО Магнум Кэш энд Кэрри → Magnum»). Недетерминировано, работает только когда включён AI, не даёт ни домена, ни QID, ни иконки. На нём уже висят отчёты: `spend-flow.service.ts:53`, `goal-flow.service.ts:499`, детектор подписок.
- `subscriptions.vendor_domain` — заполняется только руками, поэтому у большинства подписок иконки нет.
- `backend/src/modules/geocoding/geocoding.service.ts` — self-hosted Nominatim (опционален, `GEOCODER_URL`), пока только `/search` (адрес → точка).
- `receipts.metadata.captureLocation` (lat/lng из EXIF или устройства) и `parsedData.merchantAddress` — для чеков у нас часто есть координаты.
- `transaction-categorizer.ts` — локальные эмбеддинги (`@huggingface/transformers`, MiniLM) уже в проде: fuzzy-слой есть чем закрыть, если понадобится.
- `categorization-rule` + `category-learning` — готовый прецедент «правка пользователя превращается в правило».

## 3. Что я проверил руками (а не по описаниям)

NSI-данные скачаны и прогнаны локально (`dist/json/nsi.min.json` 12.2 МБ, `dist/wikidata/wikidata.min.json` 9.9 МБ, npm-пакет целиком — 98 МБ распакованного).

**Факт 1. У NSI есть свой `Matcher`, но он не для наших строк.** Он требует (а) чистое имя и (б) известную пару OSM-тегов:

```
match('office','coworking','WeWork')                 -> wework-cfb41b   ✅
match('office','coworking','WeWork Kurfürstendamm')  -> null            ❌
match('shop','supermarket','LIDL SAGT DANKE 12345')  -> null            ❌
match('amenity','cafe','Starbucks Coffee')           -> starbucks (alternate) ✅
```

То есть `Matcher` годится как финальная проверка, но кандидат-генерацию придётся писать свою.

**Факт 2. Наивный поиск подстроки по NSI даёт уверенные ложные срабатывания.** Прогон по нашим же названиям из скриншота:

| Вход | Наивный матч | Вердикт |
|---|---|---|
| `WeWork Kurfürstendamm` | WeWork (wework.com, логотип есть) | ✅ |
| `The Barn Coffee Roasters` | The Barn (thebarn.de) | ✅ |
| `LIDL SAGT DANKE 12345` | Lidl (lidl.de) | ✅ |
| `MCDONALDS 1234` | McDonald's | ✅ |
| `Deutsche Telekom AG` | Deutsche Telekom | ✅ |
| `Nobelhart & Schmutzig` | **HART** (автобусный маршрут) | ❌ |
| `Five Elephant` | **Le Five** (спортзал во Франции) | ❌ |
| `SpaceShip` | **Spaces** (коворкинг) | ❌ |
| `PAYPAL *SPOTIFY` | **Spot** (магазинчик) | ❌ |
| `Café Einstein Stammhaus` | **Haus!** (кафе в Индонезии) | ❌ |
| `AMZN Mktp DE*1A2B3`, `SBUX 0421`, `Netflix.com`, `Uber BV` | нет матча | ❌ (нужен слой очистки и онлайн-брендов) |

Вывод для архитектуры: **совпадение только по границам токенов, обязательный фильтр по стране (`locationSet`), приоритет `brands/*` над `operators/*`, порог уверенности — и «не знаю» как нормальный ответ.** Неверный бренд хуже отсутствующего: он поедет в отчёты, подписки и категории.

**Факт 3. Берлинская независимая гастрономия в NSI не живёт.** `Nobelhart & Schmutzig`, `Five Elephant`, `Café Einstein` — это POI в OSM, а не сети. Их закрывает только геопуть (координаты чека → Nominatim/Overpass), и именно для чеков у нас координаты есть.

**Факт 4. Размер нам подходит.** Сжатый индекс (бренды + операторы, все варианты имён, QID, сайт, URL логотипа) — **43 276 записей, 10,6 МБ JSON / 1,9 МБ gzip**. Это не зависимость в 98 МБ, а таблица в Postgres на ~80 тыс. строк имён.

## 4. Кандидаты, которые я рассмотрел и отклонил

- **logo.dev / Brandfetch / Context.dev / Hunter Logo API** — технически лучшие (дескриптор → бренд + лого + категория одним вызовом, бесплатные тиры до 500k/мес), но это отправка мерчантов пользователя третьей стороне, у logo.dev ещё и обязательная атрибуция в UI. Годится только как **opt-in** для облачной инсталляции, не как база.
- **openenrichment** — ровно наша задача и правильная схема (`transaction_text_regexp`, `mcc`, `icon_url`, `transaction_text_examples`), но 3 звезды и ~550 мерчантов, из них 404 австралийских. **Берём не как зависимость, а как донора:** CC0-регулярки в seed и, главное, их `transaction_text_examples` — готовый набор для тестов очистителя.
- **SVGL** — красивая галерея SVG, но это UI-ресурс без API сопоставления имён; ценности поверх simple-icons не добавляет.
- **banks-db** — BIN → банк и фирменные цвета, CC-BY-4.0, но не обновлялся с 2023 и решает другую задачу (эмитент карты, не мерчант). Можно вспомнить позже для кошельков.
- **Wikidata SPARQL вживую** — тот же контент, что уже лежит в NSI-дампе, но с сетевым вызовом на каждую строку. Дамп лучше.
- **tranx / transaction-enrichment-engine** (ML-репозитории с LoRA Qwen и эмбеддингами) — исследовательские харнессы, не библиотеки. Полезны как ориентир, если дорастём до ML-слоя; у нас для этого уже есть MiniLM.
- **MCC-датасеты (ISO 18245)** — пригодятся для категории, когда банковский фид отдаёт MCC (SimpleFIN/OFX часто не отдаёт). Отдельная маленькая задача, в этот план не входит.

## 5. Архитектура резолвера

Один сервис `brand-resolution`, вызываемый при импорте транзакции/чека и из бэкфилла. Слои идут по убыванию точности, каждый возвращает `{brandId, confidence, source}`; первый уверенный ответ побеждает.

- **L0. Правка пользователя.** `merchant_aliases` по воркспейсу: нормализованный дескриптор → бренд (или явное «это не бренд»). Всегда выигрывает, confidence = 1.
- **L1. Очиститель дескриптора** (свой код, без зависимостей). Снимает: префиксы процессоров (`PAYPAL *`, `SQ *`, `SUMUP *`, `IZ *`, `TST*`), хвосты терминалов и номеров магазинов, даты и суммы, город/страну, юрформы (`GmbH`, `AG`, `BV`, `Ltd`, `Inc`, `ТОО`, `ООО`, `S.L.`), мусор карт (`KARTENZAHLUNG`, `SAGT DANKE`, `//`, `NR.`). Попутно вытаскивает **домен**, если он есть прямо в строке (`help.uber.com`, `netflix.com`) — это сразу L4.
- **L2. Точный матч по индексу NSI.** `simplify()` из NSI (убирает диакритику, пунктуацию, `&`→`and`) по всем вариантам имени; затем матч по префиксу **на границе токена** (`wework kurfurstendamm` → `wework`), фильтр по стране воркспейса/чека через `locationSet`, приоритет `brands/*` над `operators/*`, минимальная длина 4 символа, запрет матча на generic-слова из `properties.exclude`. Финальная перепроверка через родной `nsi.Matcher` с тегами найденного кандидата.
- **L3. Гео-путь для чеков.** Есть `captureLocation` или `merchantAddress` → Nominatim `/reverse?extratags=1&namedetails=1&layer=poi` → `brand` / `brand:wikidata` / `website` POI. Это единственный способ узнать `Nobelhart & Schmutzig`. Требует `GEOCODER_URL`; без него слой молча выключен.
- **L4. Домен.** Домен из L1 или из `officialWebsites` NSI → запись бренда без NSI-ID (источник `domain`).
- **L5. Fuzzy, опционально.** `pg_trgm` по таблице имён (порог ~0.45) и только как **подсказка в ревью**, никогда не авто-применение. Эмбеддинги MiniLM — потом, если trgm не хватит.
- **L6. LLM — последним и только там, где уже работает AI-обогащение.** Нынешний `vendorNormalized` остаётся, но становится fallback'ом, а не первоисточником.

Иконка резолвится отдельной лесенкой, уже знакомой фронту: вклеенный simple-icon по slug → логотип с Wikimedia Commons из NSI (через наш же прокси, с кешем) → фавикон домена → инициалы.

### Схема данных

```
brands                 -- справочник, НЕ тенантные данные (как exchange_rates)
  id, source('nsi'|'simple-icons'|'osm'|'domain'|'manual')
  nsi_item_id, wikidata_qid, name, domain, logo_url,
  osm_tags jsonb, countries text[], icon_slug
brand_names            -- 80k строк, pg_trgm индекс по simplified
  brand_id, name, simplified, kind('primary'|'alternate'|'localized')
merchant_aliases       -- тенантные: правки и авто-решения
  workspace_id, descriptor_simplified, brand_id NULL, decision('matched'|'rejected'),
  source('user'|'auto'), confidence, created_by
transactions.brand_id, receipts.brand_id, subscriptions.brand_id   -- nullable FK
```

Справочник заполняется скриптом `scripts/build-brand-index.ts`: качает два JSON от NSI фиксированной версии, сжимает до нашего формата, пишет в БД. Запускается миграцией при первом деплое и руками при обновлении NSI. В Docker-образ кладётся сжатый артефакт (1,9 МБ), npm-зависимость на 98 МБ не ставим.

## 6. Фазы (каждая проверяема)

**Фаза 0. Золотой набор — до всякого кода.**
Выгрузить 300–500 реальных `counterparty_name` / `parsedData.vendor` из dev-базы (анонимизировать суммы), разметить ожидаемый бренд руками, добавить `transaction_text_examples` из openenrichment. Файл `backend/@tests/golden/brands/cases.json`.
→ Проверка: тест гоняется под `GOLDEN_ENABLED=1`, печатает precision/recall/«не знаю». До резолвера baseline = 0 %.

**Фаза 1. Справочник и индекс.**
`scripts/build-brand-index.ts`, таблицы `brands` / `brand_names`, миграция (**нужна метка `db-approved`**), сид.
→ Проверка: в БД ≥ 40 000 брендов и ≥ 78 000 имён; `SELECT` по `simplified = 'wework'` возвращает wework.com за < 5 мс.

**Фаза 2. Очиститель + L2 + L0.**
`merchant-descriptor.util.ts` (чистый, без I/O, юнит-тесты на каждое правило), `brand-resolution.service.ts`, таблица `merchant_aliases`.
→ Проверка на золотом наборе: **precision ≥ 98 %** среди авто-применённых, recall ≥ 60 %, ноль матчей из списка ложных в §3 (это отдельные регресс-кейсы).

**Фаза 3. Иконки и UI.**
`brand_id` на транзакции/чеки/подписки; `VendorIcon` получает `brandId`; прокси иконок учится отдавать логотип с Commons; в «Top spenders», таблице выписок и подписках — каноническое имя + иконка; в строке мерчанта — «изменить бренд» (это пишет L0-алиас).
→ Проверка: живой прогон на стенде, скриншот того же экрана «Top spenders» с иконками; `npm --prefix frontend run lint:fix` (Biome **и** ESLint) и type-check зелёные.

**Фаза 4. Гео-путь для чеков.**
`geocoding.service` получает `reverse()`; резолвер использует его для чеков с координатами.
→ Проверка: на чеках с GPS из демо-данных определяются независимые кафе; без `GEOCODER_URL` всё работает как раньше (тест на выключенный слой).

**Фаза 5. Бэкфилл и обучение.**
Фоновая задача «перерезолвить воркспейс», экран «Мерчанты» со слиянием/переименованием, правка пользователя становится алиасом и перекрывает авто-решение для будущих импортов.
→ Проверка: бэкфилл на демо-воркспейсе идемпотентен (повторный прогон не меняет ни строки), правка переживает повторный импорт того же файла.

**Не входит в план:** MCC-категоризация, логотипы банков по BIN, подмена существующей LLM-категоризации, платные API.

## 7. Риски и решения, которые нужно принять

1. **Приватность фавиконов.** Сейчас прокси ходит в DuckDuckGo только за подписками (единицы доменов). Если мы включим иконки на все транзакции, DuckDuckGo со временем узнает список мерчантов пользователя (без сумм, но это всё равно профиль трат). Предлагаю настройку инстанса: `offline` (только simple-icons + Commons) / `favicons` (как сейчас) — по умолчанию спросить при первом включении. **Нужно твоё решение, что ставить дефолтом.**
2. **Товарные знаки.** Показ логотипа рядом с названием мерчанта — номинативное использование, это нормально. Чего не делаем: не отдаём наш справочник логотипов как публичный API и не кешируем картинки дольше, чем нужно для показа.
3. **Атрибуция.** OSM/Nominatim — ODbL, нужна строка «© OpenStreetMap contributors» там, где показан гео-результат (на карте чеков она уже есть). NSI — BSD-3, нужна строка лицензии в `docs/`/NOTICE.
4. **Неверный бренд дороже отсутствующего.** Поэтому порог высокий, fuzzy — только подсказка, и «Uncategorized»-подобное состояние «бренд не определён» остаётся легальным. В ревью-инбоксе (фаза 1 прошлого цикла) это естественное место для подтверждений.
5. **Обновление NSI.** Релизы раз в несколько недель. Обновляем явным прогоном скрипта + прогоном золотого набора, а не автоматически: смена `itemID` может переклеить бренды.

## 8. Открытые вопросы

- Дефолт для §7.1 (offline / favicons)?
- Нужно ли каноническое имя **заменять** показываемое (`WeWork Kurfürstendamm` → `WeWork`) или показывать бренд иконкой и подсказкой, а строку оставлять исходной? От этого зависит, ломаются ли привычные группировки в отчётах.
- Делаем ли справочник общим для всех воркспейсов инстанса (так дешевле и точнее) — подтверди, что это не конфликтует с правилом тенант-изоляции: сами бренды обезличены, тенантными остаются только `merchant_aliases`.
